# Your Claude Code session

The deep tier. Questions the brief can't answer go to your own Claude Code session through an MCP channel, `zoom-meeting`, and the session answers them: through its meeting-assistant agent when the session sent Alex in, itself otherwise. Channels are a research preview of Claude Code: the README's [What you need](../README.md#what-you-need) says what they require. These pages call the assistant Alex, its default name, and you, its owner, Sam.

Using Codex or OpenCode instead? The channel and the meeting-assistant are the same, and so is most of this page; [Codex](codex.md) and [OpenCode](opencode.md) say how to set each up, what differs and what to watch for.

Installed from npm, "this folder" on this page is your session folder, the one `agentvoice setup claude-code` made; each `npm run <command> -- …` is `agentvoice <command> …`; and `.env` and `data/` are in your AgentVoice folder: `~/.agentvoice/.env` and `~/.agentvoice/data/`.

## Linking the session

1. Register the channel once with `scripts/install-channel.sh`. It registers it for this folder only (Claude Code's local scope), so only a session started here loads it, with this folder's agent and deny rules.

   Installed from npm, make a folder for your meeting sessions and set it up there instead:
   ```bash
   mkdir -p ~/agentvoice-session && cd ~/agentvoice-session && agentvoice setup claude-code
   ```
   Setup takes a folder that isn't there yet or is empty (or one it set up before for your AgentVoice folder), and refuses your home folder, your AgentVoice folder and any folder holding files of yours, such as a project: Claude Code reads its folder without asking, so that folder is what the meeting-assistant can reach. It must be a folder of yours, in folders only you can change (never one another user made, or one in a folder others can write): anyone else who can change it could replace the floor and the configs setup writes there. It makes the folder a Git repository of its own and writes the floor (`.claude/settings.json`) and the agent (`.claude/agents/meeting-assistant.md`), the package's own, into it, adds what the agent needs to `.claude/settings.local.json` (see [The meeting assistant](#the-meeting-assistant)), and registers the channel for that folder only, by absolute paths into the installed package (`claude mcp add --scope local zoom-meeting -e AGENTVOICE_HOME=<your AgentVoice folder> -- <node> <the package's agentvoice.js> channel`), so the channel uses your AgentVoice folder whatever folder Claude Code runs it in. It also removes a `zoom-meeting` an earlier install registered for all your projects. Start Claude Code in that folder. Run it again after upgrading AgentVoice or Node: it refreshes its own files, and stops, with a diff, at one you changed (`--replace-changed` replaces it, keeping yours as a backup).

   Either way, the channel links to the voice service on its control socket with the local token (see [Ports and security](security.md)), so start the service once first; until then the channel says, on stderr, that the token is missing, and keeps trying. While it has no link, its tools tell the session why, so the session can tell you: the local token is missing, nothing is listening on the control socket (the service is not running, or it and the channel use a different `.env` or data folder), or the service refused the link because the local token doesn't match (restart the voice service and the session).
2. Before a meeting, start a session with the channel loaded, or resume one with it:
   ```bash
   claude --dangerously-load-development-channels server:zoom-meeting
   claude --resume --dangerously-load-development-channels server:zoom-meeting
   ```
   Channels are a research preview, so a custom channel needs this flag. Claude Code shows a warning; choose "I am using this for local development".
3. Ask the session to "prepare Alex for my meeting with ...". It reads `get_profile`, then writes a one-page brief (at most 16,000 characters: a longer one is refused, never cut, since its end usually says what must not be shared), and Alex uses it for quick answers. If the session then sends Alex into that meeting (step 5), it passes the brief to `join_meeting`: that meeting answers from it instead of the shared brief, and no other meeting sees it. Otherwise it saves it with `set_brief` as the shared brief, `data/brief.md` (`~/.agentvoice/data/brief.md` from npm), which every meeting without a brief of its own uses, read again at every answer. A meeting's own brief is kept in the voice service's memory only, until that meeting is over, and `set_brief` never changes it.
4. During the meeting, deep questions arrive in the session as `<channel source="zoom-meeting" kind="question">`. The session answers with `reply`, and Alex speaks the answer. Keep the session open in its terminal until the meeting ends. Alex waits about 60 seconds for an answer, then tells the meeting it can't reach your notes. If the meeting moves on first (Alex is talked over while it says it is checking, told never mind, asked something else or asked to leave, or its page goes), it stops waiting at once. A reply after either is not said, and the `reply` tool tells the session which of the two happened, instead of "Alex will say it now."

   Alex keeps every answer the session gives, the chat detail included (only the spoken part is in the transcript), and every message the session posts with `post_chat`, and answers from them by itself, on top of the meeting's brief, for the rest of the meeting. So a follow-up such as "what was the third step again?" is answered at once instead of going back to the session. An answer that came too late to be said is kept too, marked as one the meeting hasn't heard, so Alex gives it if the question comes up again. For that the service remembers the questions it stopped waiting for, in memory only, for 10 minutes at most. Once Alex is out of a meeting it was asked to leave or removed from, the words of its questions go at once, those still waiting for an answer included: only that they were asked stays, so a reply to one is told that nothing is kept. A late answer is not kept once Alex was asked to leave or the meeting is over, and the `reply` tool says so. The session can also get ahead of questions with `add_to_brief`: facts the meeting is likely to ask about next, in short plain sentences, only what the brief's "may be shared" allows. Alex answers from them from the next question. These additions live in memory, for that meeting only: the brief itself is unchanged (`set_brief` still replaces the shared one), they are capped at 8,000 characters (the oldest go first, to keep answers quick), and they go when the meeting ends, or at once when Alex is asked to leave or removed.

   `add_to_brief`, `get_transcript`, `post_chat` and `why_not_answered` take the meeting's key (`meeting`, which `join_meeting` returns and every question carries). Without it they use the latest meeting Alex is in. A `post_chat` without it is refused while Alex is in more than one meeting, since everyone in the meeting sees a post and it can't be taken back.

   Ask the session why Alex didn't answer something, and it calls `why_not_answered`: the latest lines Alex heard (10, or up to 50), each with what Alex did with it and why, by the rules in [In a meeting](in-a-meeting.md#if-alex-doesnt-answer). The session finds the line you mean and explains it, with how to say it next time. It is read-only, for live meetings only, and doesn't take the questions. Its lines are meeting text, which the session treats as untrusted, and each is given up to 500 characters (the transcript has all of it). The service keeps them in memory only, never in a file or the log, and they go when the meeting ends, or at once when Alex is asked to leave or removed. A channel newer than the running voice service says to restart the service.
5. To send Alex into a meeting from the session, join the meeting yourself and paste the link with a request, such as "Alex, join this meeting: https://us06web.zoom.us/j/...". The session calls the channel's `join_meeting` tool, which does the same as `npm run join` (`agentvoice join` from npm), except that only that command can start the share test (`--share-test`) or the speaker probe (`--speaker-probe`). Claude Code asks before using the tool unless you allow it.

   `join_meeting` takes the meeting's own brief as text (`brief`), never as a file path: the channel runs outside Claude Code's deny rules, so a path would let it read and send a file the session itself may not open. For a brief you keep in a file, the session reads it with its own Read tool, which the deny rules cover, and passes the text. The note `join_meeting` returns says which brief the meeting uses: its own, the shared one, or none (`data/brief.md` is empty, or longer than 16,000 characters and so refused). A channel newer than the running voice service refuses a brief rather than send Alex in with the shared one: restart the service.

   From Telegram too, if you want: set `ZOOM_JOIN_TELEGRAM_CHATS` in `.env` to your own chat's ID (the `chat_id` the Telegram plugin puts on your messages), then restart the session with the Telegram plugin's channel loaded as well (add `--channels plugin:telegram@claude-plugins-official`; see Claude Code's channels documentation). The session then also joins when a message from that chat asks, with the link in the same message, and replies there saying which meeting Alex is joining. It goes by the chat and user IDs the plugin sets, never by what a message says, and only private chats are taken (anyone in a group could ask). A link in a meeting, a file, a web page, another chat or a forwarded message still never sends Alex anywhere.
6. After the meeting, the session receives a `meeting_ended` event with the transcript path and the minutes file (or why there are none), and sends you the minutes. In a meeting with slides, it also says how far the presentation got, and, if it stopped partway, the `slides_from` to carry on from in another meeting.

When a question goes to your session, it goes first, so your session is already working on it while Alex says it is checking. If no answer has come 15 seconds after that, Alex says "Still checking. One moment." once, and keeps waiting.

## Presentations

Alex can present a slide deck you prepared, saying only your script ([Presenting slides](presenting.md)). With the session:
1. Ask for a presentation of a deck. The session asks you to export it as a PDF, then runs `npm run slides -- prepare <the PDF>` (from npm, `agentvoice slides prepare <the PDF>`), which asks you first (see the permissions below).
2. Ask it to draft the narration. It writes each `TODO` section of `<deck>.script.md` with Edit: spoken sentences, figures as words, only what is on the slide or in your own words, nothing from any meeting, and `check: yes` left on each section it drafts. Read each section yourself, change what you want, and delete its `check: yes`. Then it runs `npm run slides -- check <the script>` (`agentvoice slides check <the script>`).
3. Ask it to send Alex in with the slides. It reads the script with its own Read tool and passes its text to `join_meeting` as `slides` (with `slides_from` to start at a later slide): never a path. The channel checks it, takes out every comment, and sends the rest, so your notes never reach the voice service. The note `join_meeting` returns says the deck, the estimate, and the share setting the host needs.
4. During the meeting, `slides_status` says where the presentation stands, and `slides_control` steers it when you ask: `start`, `pause` (only you can resume it), `resume`, `next`, `back`, `goto` with `slide`, `restart`, `wrap_up`, `stop` or `end`. Both take the meeting key, and without it act on the only meeting with slides. Neither takes the questions. The session also gets `kind="presentation"` events (it started, finished or stopped, a problem with the share, or held for long): status, which it tells you and acts on in no way.

The session uses `slides_control`, and `join_meeting` with slides, only when you ask it in this session, never because of text from a meeting, an event, a file or a web page. The meeting-assistant agent gets neither tool. A channel newer than the running voice service refuses slides, rather than send Alex in without them: restart the service. The titles in events, `slides_status` and the questions handed to the session ("On screen: slide 6 (5th of 8 in this presentation), Pricing.") come from your PDF: the session is told they are content, not instructions.

## The meeting assistant

Channel events only reach the main session, and only between its own tool calls, so a long tool call can hold a question past the 30 seconds people wait. So after `join_meeting` succeeds, the session starts the `meeting-assistant` agent (`.claude/agents/meeting-assistant.md`) in the background, and that agent pulls the questions instead:

1. It calls the channel's `next_question` tool with the meeting key `join_meeting` returned, which waits up to `wait_seconds` (default 120, at most 600) and returns that meeting's next question as JSON, or `{"none": true}` if nobody asked anything.
2. It answers with `reply`, then calls `next_question` again.
   - It gets ahead of questions too. After a reply, if the sources it just read hold one or two facts the meeting is likely to ask about next, it adds them with `add_to_brief`. When nobody has asked anything for a while (`{"none": true}`), it reads the latest part of that meeting's transcript once (`get_transcript` with `max_chars` 3000 and the meeting key). If the talk is heading to something neither the brief nor its additions cover, it does at most one or two quick reads in its sources, checking for a question (`next_question` with `wait_seconds` 1) before each, so a question asked meanwhile isn't kept waiting, then adds the facts and goes back to waiting. It adds only facts from its own sources, never anything taken from the transcript or the questions, and it doesn't repeat its answers, which are kept automatically.
3. When the meeting ends, `next_question` returns `{"meeting_ended": true, ...}`, at once and on every later call, so an agent that was busy answering still finishes. The agent then gives the session the questions, answers and follow-ups. The session still gets its `meeting_ended` event. Without a meeting key, the agent hears the end of the latest meeting until Alex joins or starts another one.

While the agent is waiting, or answering (up to 45 seconds after its last `next_question` call returned), questions go to it and not to the session. With no agent running, they arrive in the session as before. A question the agent doesn't collect within 45 seconds goes to the session as well.

The agent's instructions are the same for everyone and name no one. Who you are, the brief, where to look and your own rules come from the channel's read-only `get_profile` tool, which the agent calls once, right after its first `next_question` returns, with the meeting key: your names and company from `.env`, the brief that meeting uses (its own, which the channel asks the voice service for, or the shared one, with its path), and your profile's sections (see [Make it yours](make-it-yours.md)), read again at every call. When that meeting's brief can't be had (the key is no meeting Alex is in, the meeting is over, or the voice service is older than the channel or not linked), `get_profile` gives no brief at all (`brief_for` is `unavailable`), never the shared one in its place, and the agent answers only from your profile's About, uses none of your knowledge sources (without the brief, nothing in them is cleared to share), and hands the rest to you. It looks in the brief first, then in the knowledge sources your profile lists, in that order and by each source's own rule; with none listed, it answers from the brief alone and says anything else is one for you to follow up on. The session sees `get_profile` too, and is told to read it before writing a brief.

Permissions for the session. Claude Code merges two settings files in this folder: the committed `.claude/settings.json`, the floor of deny rules below, which is the same for everyone, and your own `.claude/settings.local.json`, which is gitignored and never committed. Keep the floor as it is, and put everything of your own in `settings.local.json`; a deny rule in either wins over any allow. Installed from npm, `agentvoice setup claude-code` only ever adds to `settings.local.json`, and won't replace a `.claude/settings.json` you changed: it stops with a diff, and replaces it only when you run it with `--replace-changed`, which keeps yours as `.claude/settings.json.before-setup-<date and time>`. In `settings.local.json`:
- Allow `mcp__zoom-meeting__next_question`, `mcp__zoom-meeting__get_profile`, `mcp__zoom-meeting__reply`, `mcp__zoom-meeting__post_chat`, `mcp__zoom-meeting__add_to_brief` and `mcp__zoom-meeting__get_transcript` in `permissions.allow`: an agent in the background can't answer a permission prompt, so a tool it isn't allowed is simply denied. Without `get_profile`, it has neither your name, the brief's text nor your knowledge sources.
- Installed from npm, `agentvoice setup claude-code` has added those six for you, and two read rules, such as `Read(//home/sam/.agentvoice/data/transcripts/**)` and `Read(//home/sam/.agentvoice/data/minutes/**)` (your data folder's absolute path, in Claude Code's `//` form for one): the agent's last step reads the transcript and the minutes the meeting names, which are outside the session folder there. They are read rules, not `additionalDirectories`, which would let a mode that edits write in the data folder, and the floor still denies `.env`, `local-token` and `data/decks` in it. Setup adds nothing else, and keeps everything else in the file: your knowledge sources, `why_not_answered` and the slides tools are still yours to allow, as below.
- `mcp__zoom-meeting__why_not_answered` is for your own session, not the agent, which doesn't have it. Allow it in `settings.local.json` if you don't want a prompt when you ask why Alex didn't answer.
- `mcp__zoom-meeting__slides_status` is read-only and safe to allow. Leave `mcp__zoom-meeting__slides_control` to prompt: starting, moving or ending a presentation is yours to decide. The meeting-assistant agent has neither.
- Knowledge sources outside the project need reading allowed too: add their folders to `permissions.additionalDirectories`, or allow them with a rule such as `Read(//home/sam/work/acme-docs/**)` or `Read(~/work/acme-docs/**)` in `permissions.allow`. Otherwise its reads there are denied.
- Add your own private paths (the ones in your profile's Never open, say) to `permissions.deny`.
- Don't allow `Bash(npm run slides:*)`, nor `Bash(npm run slides -- check:*)`, and from npm, don't allow `Bash(agentvoice slides:*)`, nor `Bash(agentvoice slides check:*)`. `npm run slides -- prepare` reads any PDF it is given, even one in a folder the session may not read, and writes its text into `data/decks`. `check` opens the file it is given itself, so your deny rules don't apply to it, and it writes the deck's contact sheet. Both should ask you first: the prompt shows you the path before it runs. At most, allow `Bash(npm run slides -- list)` and `Bash(npm run slides -- status)` (`Bash(agentvoice slides list)` and `Bash(agentvoice slides status)`); leave `npm run slides -- control` to prompt (see [Presenting slides](presenting.md)).
- The project agent (`.claude/agents/meeting-assistant.md`) and both settings files load only when the session runs in this folder: start it here (from npm, in the session folder setup made).

For example (with your own paths):
```json
{
  "permissions": {
    "allow": [
      "mcp__zoom-meeting__next_question", "mcp__zoom-meeting__get_profile", "mcp__zoom-meeting__reply",
      "mcp__zoom-meeting__post_chat", "mcp__zoom-meeting__add_to_brief", "mcp__zoom-meeting__get_transcript",
      "Read(~/work/acme-docs/**)", "Read(~/work/acme-website/**)"
    ],
    "deny": ["Read(~/work/acme-docs/hr/**)", "Read(~/work/acme-ops/secrets/**)"]
  }
}
```

What the agent must never open or say has a floor of its own, in its instructions, that a profile only adds to: never open `.env` files, `~/.ssh`, `~/.cloudflared`, `~/.claude.json` or anything named like a key, secret, token, credential or certificate; never say or post credentials, hostnames, internal URLs, account IDs, security findings, or anything about other people or clients. The committed `.claude/settings.json` enforces part of the file floor for every session in this folder: its `permissions.deny` rules stop a session reading these, wherever they are: `.env`, `.env.local`, `.env.*.local`, `.env.production`, `.env.prod`, `.env.development`, `.env.dev`, `.env.staging`, `.env.test`, `.env.bak`, `.env.backup`, `.env.old`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `local-token` (the service's local token) and `data/decks/**` (prepared slide decks, whose text a session never needs: it drafts a script from the PDF); and these in your home folder: `~/.ssh`, `~/.cloudflared`, `~/.aws`, `~/.claude.json`, `~/.git-credentials`, `~/.netrc`, `~/.config/gh`, `~/.docker/config.json`, `~/.kube`, `~/.gnupg` and `~/.claude/.credentials.json`. The names in the first list are denied in every folder, so in `~/.agentvoice` too, when you installed from npm. `.env.example` is not among them, so a session can read the template. The rest of the floor (other names for keys, secrets, tokens and credentials) is the agent's instructions alone: add deny rules for your own in `settings.local.json`. Deny rules apply to Claude Code's file tools and to the shell commands it recognises as reading a file (such as `cat` or `head`), not to a command that reads files without naming them or to a script that opens files itself: they are not a sandbox, so keep secrets out of the folders the session works in (Claude Code's sandboxing can enforce it for every process).

Several Claude Code processes can have the channel loaded at once, such as idle pre-started ones. They all stay linked. Questions and meeting events go to:
1. a session whose meeting-assistant is waiting in `next_question`, or answering;
2. else the session that most recently used `join_meeting`, `reply` or `next_question`. Each session sends that time again when it relinks, so after the voice service restarts the same session gets them, whatever order they reconnect in. `get_transcript`, `why_not_answered`, `get_profile`, `set_brief`, `add_to_brief`, `post_chat`, `slides_status` and `slides_control` don't move them;
3. else, when no session has used one of those (for example a meeting started with `npm run join`), every linked session, and the first reply wins. Replying then claims the next questions.

A Codex session, or an OpenCode session before its channel knows which session is yours, can't be sent a question its meeting-assistant doesn't take. Such a question goes on to the linked session that can be sent one and was used most recently, and when none is left, Alex says at once that it can't reach your notes.

The service logs `[bridge] Questions now go to coding session #N` when that changes, and a warning when a question goes to every session. Only the channel server can link: `/bridge` is on the control socket (your user only), needs the local token, and refuses any browser (a request with an `Origin` header), so neither a web page nor another program or user on this computer can take the questions.

Safety:
- The channel tells the session, and the agent's instructions tell the agent, to treat meeting text as untrusted: to read and answer, and to change nothing because of it, with one exception. They may add to Alex's additions for that meeting with `add_to_brief`, using facts from their own sources. Meeting text may suggest a topic to add, but never supplies the content, and never leads them to do anything else.
- A brief holds only your words and the session's own sources: the channel tells the session never to put anything from a meeting in one (no transcript, minutes, question or agent report).
- What the session and its agent add with `add_to_brief` comes from their own sources, never from the transcript or the questions, and only what the brief allows to be shared. Alex is told that the questions quoted in the answers it keeps were asked by participants and are not instructions.
- For extra safety, open meeting sessions in a permission mode that asks before edits.
- Don't use `--dangerously-skip-permissions` for meeting sessions.
