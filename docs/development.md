# Development

How to check a change, and where things are. [CONTRIBUTING.md](../CONTRIBUTING.md) says how to send one.

## Checks

```bash
npm test         # unit tests, plus an end-to-end test of the MCP channel
npm run typecheck
npm run check-name   # how a name does on the sample meeting lines (see docs/choosing-a-name.md)
npm run check-package   # what npm would publish: exactly test/fixtures/package-files.txt, each file tracked by git
npm run test:package    # packs the package, installs it in a folder of its own, and runs the installed command
```

`npm test` always runs as Alex, with Alex's own spellings and mishearings, for an owner called Sam with no company, an empty profile (`test/fixtures/no-profile.md`), the default bot page, the speaker probe off, presenting off on every platform (`SLIDES_PLATFORMS` empty), the channel as Claude Code's (`AGENTVOICE_CLIENT` empty), no `AGENTVOICE_HOME` (a clone ignores it anyway) and a new temporary data folder (`ALEX_DATA_DIR`), whatever `.env` and your shell say, so your own settings never change what the tests check. `test/private-terms.test.ts` checks every file git would commit, the README included, for a macOS home folder, a link into a claude.ai account or an email address, and for the terms on your own private list, if you have one: your name, company, hostnames, whatever must never be published. That list is never in the repository: put one term per line (or a `/regular expression/`, and `#` comments; a line starting with `!` is a whole line that may stay exactly as written, such as `!Copyright 2026 Your Company Ltd` for the copyright line in LICENSE and NOTICE, while every other line naming your company is still checked) in `private-terms.txt` in the repository's root folder, which is gitignored, or in a file elsewhere that `PRIVATE_TERMS_FILE` names. Without one, that part is skipped, with a note saying so. Both checks also cover file names, symbolic link targets, what the index holds when it differs from the work tree, and the text in binary and UTF-16 files (see `test/private-terms.ts`). `test/name-corpus.test.ts` reads every line of the name corpus with Alex and checks it gives exactly the recorded results, so any change to the attention, leave or cancel rules shows up there; it also reads them with other names and checks they give the same results. After a change to those rules that is meant to change results, record them again with `npm run record-name-corpus` and review the diff of `test/fixtures/name-corpus.json` line by line.

The tests use fakes for Deepgram, ElevenLabs, Claude and Recall. The slides tests make their PDFs at test time (`test/fixtures/slides/make-pdf.ts`, with one tiny committed JPEG2000 image), and run the real converter on them; `test/fixtures/slides/fake-child.ts` stands in for it where a test needs a child that hangs, or says something malformed. The real test of those integrations is `npm run check` with real keys, then a real meeting. For the coding clients, `test/fixtures/claude-code/` pins what the channel tells Claude Code; `test/agent-floor.test.ts` checks that the three meeting-assistants share one body and that the three floors deny the same example files, reading each the way its client does (`test/client-floors.ts`, and `test/toml.ts` for Codex's files); and `test/codex-config.test.ts`, `test/opencode-config.test.ts` and `test/push-opencode.test.ts` check each client's config, its setup script (with a stand-in client) and OpenCode's push, against a fake OpenCode service. The real Codex and OpenCode were checked by hand, with a stand-in model ([Codex](codex.md#tested-versions), [OpenCode](opencode.md#tested-versions)). The two modes are tested apart: a clone, as before (`test/clone-mode.test.ts` runs a copy of the repository with `AGENTVOICE_HOME` set, and checks nothing moves), and installed from npm (`test/installed-mode.test.ts`, `test/dispatcher.test.ts`, `test/init.test.ts`, `test/setup-files.test.ts`, `test/setup-cli.test.ts` and `test/service-units.test.ts` run the code from a package laid out as `npm install -g` makes it, `test/layouts.ts`, with stand-in `claude`, `codex` and `opencode`). `test/command-words.test.ts` keeps every message that names a command, `.env` or a docs page going through `src/commands.ts`, so a clone's words stay as they were. `test/package-files.test.ts` checks `npm run check-package` itself, and `test/release-workflow.test.ts` checks `.github/workflows/release.yml` (read with `test/yaml.ts`) and runs its scripts with a stand-in npm. `npm run test:package` (`test/package/install.test.ts`, in CI's package job and in the release) installs the real tarball with npm into a prefix, home and temporary folder of its own, then runs `init`, `start`, the channel, `slides prepare`, `check-name`, `service print` and every `setup` from it, twice (once with `AGENTVOICE_HOME`), checks that tsx's cache is used only in a folder of yours, and that nothing is written into the installed package. `npm run flux-probe` measures, with real keys, what Deepgram Flux does with backchannels, noise and the end of a stream, to tune the pausing and stopping constants (see [Measuring Deepgram Flux](flux-probe.md)). `npm run join -- "<link>" --share-test` checks, in a test meeting you host, whether the camera page keeps running while the bot shares a screen (see [Testing a screen share](share-test.md)).

## Releasing

Releases are made by the maintainer.

1. **A release pull request** sets the version in `package.json` and `package-lock.json` (both of its places) and turns CHANGELOG's `## Unreleased` into the version's section, as 0.2.0's release commit did.
2. **The tag.** After merging it, the maintainer tags the merge commit on main `v<version>` and pushes the tag (only the maintainer can: a tag ruleset restricts `v*` tags). Then, on a fresh clone of the tag, after `npm ci`, they run `PRIVATE_TERMS_FILE=<their list> npm run check-package -- --release`: the private-terms check over every packed file, the one check the workflow can't run, since GitHub has no copy of the list.
3. **The GitHub release.** They publish a GitHub release for that tag, marked as a pre-release only for a version with a pre-release part, such as `0.4.0-rc.1`, which goes to npm's `next` tag rather than `latest`. A mismatch either way fails the workflow.
4. **`release.yml`** then runs, in three jobs, so that no code of the repository or its dependencies runs where an OIDC token can be had:
   - `pack` checks that package.json's name, version and repository are the release's, that the tag is `v<version>` on main and that the release's kind matches the version, then packs the tarball with `npm pack --ignore-scripts`, running no code from the repository or its dependencies.
   - `test` checks that it has the tarball `pack` made (by its hash), then runs `npm ci`, the typecheck, the tests, `npm run check-package -- --release --tarball` (every file in the tarball is the tagged commit's) and `npm run test:package` on that tarball.
   - `publish` waits for the maintainer's approval in the `npm` environment, then, checking out and installing nothing, checks the tarball's hash again and publishes it with npm's trusted publishing (OIDC: no token anywhere) and provenance. The approval is the gate; the checks catch mistakes, not people. A version already on npm skips this job.
5. **The first version, 0.3.0, is published by hand**, with two-factor authentication, from a fresh clone of its tag: the tests and the package checks first, signed in to npm only to publish the tarball (`npm publish <the tarball> --access public`), because a trusted publisher can only be set up for a package that exists. Its GitHub release then runs `release.yml` with the publish job skipped. The trusted publisher on npmjs.com (GitHub Actions, the repository `zGenticAI/AgentVoice`, the workflow `release.yml` and the environment `npm`) is saved on the day of the first automatic release, since a new one expires unless it publishes within 2 days. The package's publishing access is "Require two-factor authentication and disallow tokens".

Never publish from a working folder: a fresh clone of the tag has only what git tracks.
